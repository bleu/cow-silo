# Security model

## Order checks

The sell token must be non-zero and different from the resource token. A fill-or-kill sell order must sell the full, positive token balance after any funding. The buy token, receiver, and app data must match the Silo's configuration. Both balance types must be ERC-20, and the fee must be zero.

The order's `buyAmount` must meet `currentMinimumBuyAmount(sellToken)` at validation. The auction sets an absolute output amount for the full balance. The Silo has no price oracle. Deposits can change the amount sold without changing the required output. An order can execute at its limit.

Only the configured Settlement contract can call `Silo.commit(order)`. ERC-1271 validation requires a matching order hash and a commitment in the same transaction. Each Silo allows one active order per sell token in a batch. A later commit for the same token replaces the earlier commitment. Orders for other tokens remain active. A commit alone does not reset the auction. The Silo uses Settlement's full-fill record to confirm a sale of that token. A new sale can change a solver's quote before settlement.

## Execution deadline and fill records

The Silo derives `executionDeadline = validTo - auctionDuration()`. At commit and validation, the deadline must be between the current block timestamp and 300 seconds later, inclusive. CoW's `validTo` can be later than this deadline. This keeps the fill record available until the sold token reaches its floor, even if the order executes at the deadline. For a flat auction, `auctionDuration()` is zero and the two deadlines are equal.

Verify that the intended driver accepts the chosen CoW order lifetime. An onchain deadline check does not establish driver support.

## Administrative control

The initial amount, positive floor, and effective duration are immutable. The owner cannot withdraw fee tokens or change the resource token, recipient, Settlement contract, Vault Relayer, or app data. The owner can replace or disable the funding adapter and transfer ownership in two steps. Renouncing ownership freezes the adapter configuration.

## Optional funding

Funding starts disabled. A configured adapter gets at most 200,000 gas per `fund(sellToken)` call. The Silo ignores failure and return data. If the adapter fails, the Silo balance must still match `sellAmount`. The gas cap does not guarantee success if the outer transaction has too little gas.

`ApprovalFundingAdapter` fixes a non-zero source and Silo recipient. Only that Silo can call `fund`. The source approves the adapter as the spender. The adapter can transfer up to the smaller of the source balance and its allowance. Replacing or disabling the adapter does not revoke the source's token allowances. Revoke old allowances separately.

A commit can move source inventory to the Silo without a trade. If the outer transaction reverts, the transfer rolls back. If it succeeds without a fill, the tokens stay in the Silo and the clock does not restart. Changes to source balances, allowances, or adapter configuration can invalidate the solver's funding estimate.

Adapters have no special withdrawal rights. Review the adapter and its source permissions before granting access.

## External controls and token behavior

CoW Protocol controls solver authorization and the surplus-capturing JIT owner set. Check the intended CoW configuration before relying on either.

If the Vault Relayer allowance is too small, `commit` gives it an unlimited allowance for that sell token. Only the configured CoW Settlement contract can call the Vault Relayer. The Silo targets standard ERC-20 tokens. Rebasing, transfer fees, callbacks, and unusual approval rules need separate tests.
