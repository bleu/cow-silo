# Security model

## Enforced onchain

The Silo enforces these rules:

- The sell token is not the resource token.
- The buy token is the resource token.
- The receiver is the fixed resource recipient.
- The sell amount equals the complete current balance.
- The buy amount meets the current resource-denominated minimum.
- The execution deadline is at most five minutes ahead. CoW `validTo` also includes the auction duration.
- The app data matches the fixed app data.
- The fee is zero.
- The order is a fill-or-kill sell order.
- Both balance types are ERC-20.
- The Settlement contract committed each exact order hash in the same transaction.

Each sell token has one active commitment per Silo. A later commit for the same token replaces the first.

## Administrative control

The Silo uses two-step ownership. The owner can replace or disable `fundingAdapter`. The auction settings are immutable. The owner cannot change the resource token, recipient, Settlement contract, Vault Relayer, or app data. The owner cannot withdraw fee tokens.

Renouncing ownership permanently freezes the adapter configuration. A production protocol should use its standard governance controls as the owner.

## Optional funding

Funding starts disabled. After caller, token, and positive-amount checks, `commit` attempts `fund(sellToken)` on a non-zero adapter with a fixed 200,000 gas cap. It ignores failure and return data. An expensive adapter can fail within this cap. The cap does not guarantee success when the outer transaction has too little gas. If funding fails, the current Silo balance must still exactly match `sellAmount`; prefunding alone does not make an order for a larger amount valid.

`ApprovalFundingAdapter` fixes a non-zero source and Silo recipient. Only the Silo can call `fund`. The source approves the adapter as the actual spender, not the Silo or Vault Relayer. The adapter can transfer only the smaller of the source balance and its allowance. Replacing or disabling the adapter does not revoke the source's token allowances. Revoke old adapter allowances separately.

Source approval permits inventory to move into the Silo on a valid `commit`. A commitment does not require a later trade or signature validation. An authorized Settlement interaction can commit a matching funded balance without selling it, leaving source tokens in the Silo. The fixed recipient prevents diversion to another address; it does not guarantee that source inventory stays at the source until a completed conversion.

Changes to source inventory, allowances, or adapter configuration can make the exact-balance check revert. If the outer transaction reverts, the source transfer also rolls back. A successful commit without a trade does not roll back funding.

Adapters have no privileged withdrawal bypass. A protocol-specific adapter must use the source protocol's existing permissions. Review those permissions and adapter behavior before granting access.

## Required external controls

CoW Protocol authorizes solvers. CoW Protocol also controls the surplus-capturing JIT owner set. This set must include the production Silo deployment model.

The Silo has no price oracle. The minimum buy amount is an absolute output floor, not a price assertion. Solver competition supplies price discovery above that floor. If competition fails, an order can execute at its limit. Protocols must treat the selected minimum, CoW configuration, and solver diversity as security dependencies.

## Token behavior

The first commit for a token gives the Vault Relayer an unlimited allowance. The configured CoW Settlement contract is the only caller of the Vault Relayer.

Rebasing tokens, fee-on-transfer tokens, callback tokens, and tokens with unusual approval rules need separate tests. The current version targets standard ERC-20 tokens.
