# How it works

## Collection

A protocol can transfer ERC-20 fee tokens directly to its Silo. The Silo does not keep a list of tokens. No token registration or keeper is needed to start an auction.

The owner can also configure a funding adapter. Funding is disabled by default. With `ApprovalFundingAdapter`, the source approves the adapter to transfer inventory to the Silo. The available amount is the smaller of the source balance and its allowance to the adapter.

## Auction

All sell tokens start on the Silo's deployment timestamp, even tokens deposited later. After a full fill, only the sold token starts again, at the timestamp of the sale. A deposit, a commit without a fill, or a sale of another token does not restart its clock.

The auction sets the least acceptable output for a sale of the full balance. It uses the resource token's smallest unit. Let `initial` be `initialBuyAmount()`, `floorAmount` be `minimumBuyAmount()`, `D` be `auctionDuration()` in seconds, and `elapsed` be seconds since this token's auction started. `currentMinimumBuyAmount(sellToken)` returns:

```text
if D == 0 or elapsed >= D: floorAmount
otherwise:                  initial - floor((initial - floorAmount) * elapsed / D)
```

`floor(...)` rounds the drop down to a whole unit. For example, with an initial amount of 110, a floor of 100, and a duration of 6 seconds, the required output is 109 after one second. It reaches 100 after six seconds and stays there until the next sale. With equal amounts, the effective duration is zero and the required output is constant.

## Building an order

Solvers can find Silos through the factory's `SiloCreated` event. A solver sets `sellAmount` to the current balance plus expected adapter funding. `availableBalance` is specific to `ApprovalFundingAdapter`; other adapters need their own estimate. The order sells the full resulting balance, buys the fixed resource token, and pays the fixed recipient. Set `buyAmount` at or above `currentMinimumBuyAmount(sellToken)`. A new sale of that token can raise the required output after the solver reads it.

Use the chain's block timestamp to choose an execution deadline at most 300 seconds ahead. The CoW order field is `validTo = executionDeadline + auctionDuration()`. The Silo checks the execution deadline at commit and signature validation. The extra time keeps CoW's fill record available until a restarted auction reaches its floor. It does not give the solver extra time to execute. Verify that the intended driver accepts the chosen `validTo` lifetime.

## Settlement

Include one `Silo.commit(order)` pre-interaction for each order, with at most one active order per sell token in each Silo. A batch can include orders for different sell tokens. The Settlement contract calls `commit` with the full order; the Silo computes its hash.

If an adapter is set, the Silo attempts funding with a 200,000 gas cap and ignores failure and return data. It then checks that its balance equals `order.sellAmount`, approves the Vault Relayer if needed, and records the commitment for this transaction. Simulate the full settlement: `verify` alone checks the existing balance and does not attempt funding. A successful commit without a trade can leave funded tokens in the Silo. If the transaction reverts, funding also reverts.

During signature validation, the Silo checks the exact commitment and the current order rules. A full fill in CoW Settlement confirms the clock reset for that sell token. Transient commitments clear at the end of the transaction.

## Output

Settlement pays the executed resource-token output to the fixed recipient. A treasury can receive it directly. If the recipient is a Burner, any account can call `burn()` to send the Burner's full token balance to `0x000000000000000000000000000000000000dEaD`. This transfer does not reduce `totalSupply` unless the token implements that behavior.
