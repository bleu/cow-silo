# Contracts

## Silo

`Silo` is an ERC-1271 order owner. Most order rules are immutable. A two-step owner can change the minimum buy amount, hook gas limit, and funding adapter.

Permanent values:

- CoW Settlement contract and its EIP-712 domain separator.
- CoW Vault Relayer.
- Resource token and recipient.
- AppData JSON shape and hook target.

Managed values:

- Minimum buy amount, denominated in the resource token's smallest unit.
- Hook gas limit, initially 500,000. Zero is not valid.
- Funding adapter, initially the zero address. The owner can replace it or set it to zero to disable funding.

The owner cannot change the permanent values or transfer tokens from the Silo.

Main functions:

| Function | Caller | Result |
| --- | --- | --- |
| `setMinimumBuyAmount(amount)` | Owner only | Changes the resource-denominated execution floor. Zero is not valid. |
| `setHookGasLimit(gasLimit)` | Owner only | Changes the appData pre-hook gas limit. Zero is not valid. Emits `HookGasLimitSet`. |
| `hookGasLimit()` | Any account | Returns the current pre-hook gas limit. |
| `setFundingAdapter(adapter)` | Owner only | Replaces or disables the funding adapter. Emits `FundingAdapterSet`. |
| `fundingAdapter()` | Any account | Returns the current adapter, or zero when disabled. |
| `FUNDING_GAS_LIMIT()` | Any account | Returns the fixed adapter call gas cap of 200,000. |
| `appData(sellToken)` | Any account | Returns the complete fixed-document hash for this Silo and sell token. |
| `prepare(sellToken)` | Any account | Attempts funding, approves the Vault Relayer, and records the resulting nonzero balance for this transaction. No order or later trade is required. |
| `preparedBalance(sellToken)` | Any account | Returns the prepared balance, or zero if not prepared in this transaction. |
| `isValidSignature(hash, signature)` | Any account | Checks the order hash, prepared balance, live balance, and all order rules through ERC-1271. |
| `verify(order)` | Any account | Checks the Silo order rules and current minimum without requiring preparation. |

Preparation is token-scoped. The first successful call records a balance; further calls for the same token return without funding again. Signature validation requires the order amount to equal both this snapshot and the current full balance. Different tokens use separate transient slots. The slots clear at transaction end.

The appData template contains one pre-hook targeting this Silo, with calldata for `prepare(sellToken)` and the current `hookGasLimit` as a decimal string. The Silo rebuilds and hashes the complete document. It accepts no arbitrary appData input. Changing the limit changes the expected hash for every sell token. See the exact JSON format in the [SDK reference](/developers/sdk).

## Funding adapters

`IFundingAdapter` defines only `fund(sellToken)`. It has no required quote method, solver-supplied amount, or arbitrary bytes argument. After checking the sell token, `prepare` calls the configured adapter before reading the Silo balance. It skips funding when the adapter is zero or the token is already prepared in this transaction. The call has a fixed 200,000 gas cap; failure and return data are ignored. The cap does not guarantee that an undergassed outer transaction succeeds.

The resulting Silo balance must be nonzero. Signature validation later requires it to equal the order's `sellAmount` and the live full balance. `verify` is a view call and does not attempt funding.

`ApprovalFundingAdapter(source, silo)` requires non-zero addresses and fixes both addresses at deployment. Only that Silo can call `fund`. Its `availableBalance(token)` returns `min(balanceOf(source), allowance(source, adapter))`. Funding transfers that amount from the source to the fixed Silo, or does nothing when the amount is zero. The source must approve the adapter as the spender, not the Silo or Vault Relayer.

## SiloFactory

`SiloFactory` fixes its Settlement at deployment. The factory uses CREATE2. The owner address and user salt define the deployment salt. The caller becomes the initial Silo owner. The factory emits a `SiloCreated` event for discovery.

Creation and address prediction take the resource token, recipient, minimum buy amount, and user salt. Neither takes appData: the deployed Silo derives it from its own address and the order's sell token. This avoids a circular dependency between appData and the CREATE2 address. Adapter configuration remains a separate owner call after deployment.

The factory cannot change a Silo or move its funds. Changed creation code and constructor inputs change CREATE2 predictions. Existing deployed Silo instances are not upgraded.

## Burner

`Burner` holds one immutable token. The `burn()` function transfers its full balance to the dead address. Any account can call the function. The contract has no withdrawal function.
