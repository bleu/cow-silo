# Contracts

## Silo

`Silo` owns CoW orders and validates them through ERC-1271. Deployment fixes the Settlement contract, Vault Relayer, resource token, resource recipient, app data hash, and Settlement EIP-712 domain separator. It also fixes the auction terms:

| Getter | Type | Meaning |
| --- | --- | --- |
| `initialBuyAmount()` | `uint256` | Required resource-token output at the start of each auction. |
| `minimumBuyAmount()` | `uint256` | Output floor at the end of the auction. Must be greater than zero. |
| `auctionDuration()` | `uint32` | Effective auction duration in seconds. Equal initial and floor amounts give a flat auction with an effective duration of zero. |

Both amounts are in the resource token's smallest unit. A descending auction requires an initial amount above the floor and a positive duration. The deployment timestamp plus the effective duration must fit in a `uint32`. Read `currentMinimumBuyAmount(sellToken)` for the amount required now. The [auction calculation](/how-it-works#auction) applies separately to each sell token.

| Function | Caller | Result |
| --- | --- | --- |
| `currentMinimumBuyAmount(sellToken)` | Any account | Returns the required output for a sale of the full sell-token balance. |
| `setFundingAdapter(adapter)` | Owner only | Changes the funding adapter. Zero disables funding. Emits `FundingAdapterSet`. |
| `fundingAdapter()` | Any account | Returns the adapter address, or zero if funding is disabled. |
| `commit(order)` | Settlement only | Checks the execution window, attempts funding, checks the full balance, and approves the Vault Relayer if needed. The Silo hashes the supplied order and commits it for this transaction. |
| `isValidSignature(hash, signature)` | Called by Settlement | Decodes the order, checks its hash and commitment, and calls `verify`. |
| `verify(order)` | Any account | Checks the order rules against the current balance, required output, and execution window. Does not call the funding adapter. |
| `isCommitted(orderHash)` | Any account | Checks the transient commitment for an order hash. |

## Funding adapters

`IFundingAdapter` defines `fund(sellToken)`. It has no required quote method or solver-supplied amount. If an adapter is set, `commit` calls it before reading the Silo balance. `FUNDING_GAS_LIMIT()` is 200,000. The Silo ignores failure and return data. The resulting balance must equal `order.sellAmount`, even if the call failed.

`ApprovalFundingAdapter(source, silo)` fixes a non-zero source and Silo at deployment. Only that Silo can call `fund`. Its `availableBalance(token)` returns the smaller of the source balance and the source allowance to the adapter. Funding transfers that amount to the Silo, or does nothing if it is zero. The source approves the adapter as the spender.

## SiloFactory

Call `createSilo(resourceToken, resourceRecipient, initialBuyAmount, minimumBuyAmount, auctionDuration, appData, userSalt)`. The caller becomes the initial owner. The factory emits `SiloCreated` for discovery. Read the effective duration from the Silo when building an order.

`predictSiloAddress` takes the intended owner followed by the same arguments as `createSilo`. CREATE2 uses a salt derived from the owner and user salt, and a hash of the Silo creation code and constructor arguments. The factory cannot change a deployed Silo or move its funds.

## Burner

`Burner` holds one immutable token. Any account can call `burn()` to send the full token balance to the dead address. The contract has no withdrawal function.
